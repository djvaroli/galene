# AI capture and assistance

AI reduces the work of describing belongings and explaining options. It produces observations and proposals; application rules and the owner control persistent inventory changes. Use two narrow provider interfaces for extraction and advice, with versioned structured outputs and deterministic validation around both.

## Photo preparation

Support JPEG, PNG, WebP, and HEIC/HEIF still photos. Use Pillow plus a maintained HEIF decoder in the worker image. Accept one file per upload, at most 20 MiB and 50 megapixels, and at most ten images per scan. These are application defaults, not provider limits. Reject animated files, SVG, remote image URLs, and unsupported formats with an actionable message.

The API streams to a private temporary file with a byte limit and enqueues preparation. The worker checks actual decoding, applies orientation, removes EXIF and GPS metadata, converts to RGB JPEG, and writes a thumbnail. Preserve a normalized image with longest edge at most 2,048 pixels and a bounded output size of 2 MiB. Treat decoder warnings for excessive dimensions as errors and impose a 30-second preparation timeout in an isolated subprocess. Do not trust file extension or declared MIME type.

The browser can show a local preview when supported; otherwise show preparation progress and then the server thumbnail. Once normalized files and metadata are committed, delete the original. No original or normalized photo is public. The provider receives normalized bytes, using image data input rather than a publicly reachable photo URL.

## Extraction contract

An `ObservationBatch` includes `schema_version`, scan-level coverage notes, and at most 100 candidate observations. Each observation includes:

| Field | Meaning |
| --- | --- |
| `label`, `category` | A useful inventory description and proposed category |
| `quantity`, `quantity_basis` | Exact-looking, approximate, or unknown visible count; never a hidden count |
| `evidence_media_ids` | One or more of the supplied photo IDs |
| `visual_description` | Features useful for reviewing identity, such as color or location in the image |
| `uncertainties` | Occlusion, grouped objects, unreadable label, or another concrete limitation |
| `suggested_packing_class`, `fragile` | Nullable proposals that the owner can confirm |

There are no model-generated canonical item IDs, ownership fields, prices, weights, exact dimensions, sentimental values, or disposal actions in extraction output. Generate candidate IDs on the server. Validate supplied photo references, enums, lengths, counts, and nullable fields before saving. An empty result is legitimate; invalid or truncated output is not silently converted into an empty successful scan.

Pass the scan's images together so the model can reconcile overlapping views within the request. Ask it to identify likely repeated views without adding counts across photos. After extraction, a simple name/category search offers possible existing items from the same room, capped at five matches per candidate. All cross-scan identity decisions stay with the owner. Omit bounding boxes initially; showing the supporting photo is sufficient and avoids implying precise object localization.

Use the Responses API with image inputs and strict structured outputs. Handle refusals and incomplete responses explicitly, then perform our own semantic validation; a schema-shaped response can still describe the wrong object. [OpenAI Responses overview](https://developers.openai.com/api/reference/responses/overview), [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

Do not display model confidence as a calibrated percentage. Show concrete uncertainty notes and invite correction. Rescans never overwrite manually confirmed fields or mark missing objects disposed.

## Advice and questions

Disposition advice consumes selected saved items plus explicit preferences such as reducing volume, keeping costs down, and time available for selling. The response is a list of `{item_id, suggested_disposition, reason, missing_information}`. A recommendation based on missing information should remain conditional or undecided. Keep existing owner decisions visible and never silently replace them.

Question answering consumes an owner-scoped inventory snapshot, optional move/plan, the question, and at most six previous messages supplied by the browser. Persist the answer as a job result, not a provider-managed conversation. Each response contains text, referenced item IDs, assumptions, missing information, and the input revisions. The UI renders links only for verified item IDs present in the snapshot.

For the prototype, this is a bounded assistant request rather than an open-ended tool loop. The application selects data through ordinary inventory queries. It can answer questions such as “What fragile things are in the kitchen?” or “What is still undecided?” without embeddings or a vector store. Numerical counts and move arithmetic come from backend calculations supplied alongside the records.

Use a maximum of 1,000 inventory entries and a 40,000-token input budget, with tighter budgets for individual requests where possible. Never silently truncate an “all my belongings” question. If the context exceeds a limit, return a scope-needed response so the owner can select rooms or items. Disposition requests accept at most 100 entries; the UI can step through additional batches. Full inventory browsing and deterministic estimates are not limited by model context size.

Advice is applied through an authenticated application endpoint, with selected item IDs and the reviewed proposed values. The endpoint checks ownership, known IDs, allowed transitions, and revision freshness. The model has no direct write, filesystem, shell, SQL, web search, email, booking, or marketplace capability.

## Grounding and privacy

Treat room text, labels visible in images, owner notes, and previous messages as untrusted data. A note that says “ignore previous instructions” is inventory content. Keep fixed behavioral instructions separate from serialized input data. Do not include secrets or allow arbitrary provider URLs. Render generated text as plain text or sanitized Markdown with no raw HTML.

Before the first analysis, explain that selected room photos go to the configured AI provider. Question answering sends selected inventory descriptions and constraints; it does not automatically resend photographs. Avoid exact addresses in moving inputs when floor, access, and travel duration suffice.

Set `store=false` and use foreground provider requests from our own worker. This reduces stored response state but does not mean zero retention; provider abuse monitoring and other documented processing may still apply. Do not promise deletion from the provider when deleting a local photo. [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

## Cost and failure defaults

| Control | Initial policy |
| --- | --- |
| Model selection | Separate configured vision and advice model IDs, pinned after fixture evaluation |
| Queue size | Maximum three pending/running AI jobs for the owner; media preparation has a separate bounded queue |
| Provider deadline | 120 seconds per attempt; maximum two attempts including configured SDK behavior |
| Output bound | 8,000 tokens for scan extraction; 4,000 for advice or plan commentary |
| Daily activity | Default maximum 20 AI jobs per UTC day; configurable |
| Spending | Default target ceiling of USD 5 per UTC day, enforced using conservative request reservations and actual usage reconciliation |
| Operational visibility | Job kind, model ID, prompt/schema version, duration, token usage, estimated spend, and safe failure code |

Price configuration must be filled from the selected model's current published rates during implementation. Reserve an upper bound for images, text, output, and the possible retry before sending a request. If usage is unknown after a timeout, retain the reservation conservatively until manual reconciliation or daily rollover. Refuse paid jobs when prices are missing or the reservation would exceed the configured ceiling. Provider-side budgets may supplement this policy; do not assume they are exact hard stops. These are modest application guardrails, not a billing system.

Terminal outcomes distinguish no objects found, invalid output, provider refusal, provider outage, budget exceeded, and interruption. Show retry only where useful. Existing draft edits survive an unrelated provider failure. Plan generation always remains available without AI. When optional commentary is requested but budget or provider access is unavailable, save the deterministic plan with a “suggestions unavailable” notice instead of rejecting the entire plan.

## Short video follow-up

Accept one short clip, initially capped at 60 seconds and 100 MiB. Probe and decode inside the worker container with patched FFmpeg, a timeout, and resource limits. Drop audio. Sample at most ten frames, initially at evenly spaced intervals; let the owner select or replace blurry/redundant frames before analysis. Feed those frames into the existing photo extraction and review flow.

Record frame timestamps for evidence and delete the original video after frames are prepared. Make no claim of 3D reconstruction, exact visual tracking, or complete item coverage. Raise upload and temporary-disk limits only in the video PR, with tests for the new boundary.

## Small evaluation set

Keep five to ten consented or synthetic room scenes covering a simple desk, overlapping views, cluttered shelving, a cupboard interior, small grouped objects, and a blurry image. Human annotations define useful inventory entries and known blind spots. Keep personal photos out of Git.

Record useful detections, false objects, double counts, missed large objects, review time, latency, and cost. Compare a couple of suitable models on this same set when choosing the provider configuration. Run the paid evaluation explicitly, outside CI. CI uses recorded structured fixtures including empty output, refusal, invalid IDs, and provider failure.
